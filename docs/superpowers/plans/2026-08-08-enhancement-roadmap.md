## 決定済みの設計判断(2026-08-08 ユーザー確認済み)

| 機能 | 決定 |
|---|---|
| 1. 節をまたいだ通算分析 | 収支タブ内で「この日/通算」切替。新タブは作らない |
| 3. 直前情報 | リード側(Python)が自動タスクで定期取得→デプロイ。アプリは同一オリジンの `/tenji.json` を読むだけ |
| 4. MCP サーバー | Node/TypeScript。アプリの `lib/`(tally・raceCard・results)を直接 import して再利用 |

## 全プラン共通の制約(絶対に崩さない)

- **設計思想**: 勝つための予想ツールではない。断定的な的中表現を出さない。母数を必ず併記する。
  金額の推奨をしない(収支の「1点100円」は実績の換算であって推奨ではない)
- **アプリの外部通信は同一オリジンのみ。** 外部サイトへのアクセスはリード(Python)と
  MCP サーバー(ローカル実行)だけが行う
- **公式サイトへのアクセス礼儀**: リクエスト間隔 1.5 秒以上(collect-history.py と同じ)。
  連続 3 回失敗したらその実行は打ち切る。User-Agent はブラウザ相当の文字列を1つ決めて固定
- **買い目・収支の計算ロジック(betting.ts / tally.ts / review.ts)には触れない。**
  再利用はするが変更しない
- **既存テストを緩めない**(2026-08-08 時点でリード pytest 53 / ログ vitest 80。全部通ること)
- **git コミットはユーザーの明示指示があるまで行わない**
- 日付をハードコードしない
- スクレイピングの DOM 構造は各プランの Phase 0(実地検証)で fixture を保存してから
  パーサを TDD で書く。**fixture が正**。プラン中のセレクタ例は当てにしない

## 背景(なぜこの3本か)

2026-08-08 に過去日アーカイブ機能が完成し、`public/archive/` に開催日ごとの
出走表・結果が蓄積される構造ができた。この3本はすべてその上に乗る:

- Plan A はアーカイブを合算して「母数の増える実績」を出す(このアプリの思想の本丸)
- Plan B はアーカイブ+記録を Claude から読めるようにする(振り返りの対話分析)
- Plan C はアーカイブに「直前情報」という新しい面を足す(tenji-YYYYMMDD.json)
