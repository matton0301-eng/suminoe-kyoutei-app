# クラウド移行と自動蓄積 — 設計

> 2026-08-10 作成。現地観戦（8/9）の後、「今後も使うので毎日データを貯めてほしい」という
> 依頼を受けての設計。**まだ着手していない。** アカウントの用意がユーザー作業として要るため。

## 何を解くのか

いま自動で貯まっているもの:

| 中身 | 置き場所 | 量 |
|---|---|---|
| 番組表 | `tools/suminoe-read/cache/cards/` | 62日分 |
| 過去の競走成績 | `cache/history/` | 71日分 |
| オッズの時系列 | `cache/odds/<日付>/<HHMM>.json` | 8/9 から。36枚/日 |
| 締切直前のオッズ | `public/archive/closing-odds-*.json` | 8/9 から |
| 日ごとの出走表・展示・結果 | `public/archive/` | 3日分 |

**壁は4つ。**

1. **自宅PCが起動していないと穴が空く。** Windows タスクスケジューラで回しているため。
   `StartWhenAvailable=true` で起動後に追いつくが、その日のオッズは二度と取れない
   （オッズは過去に遡って取得できない）
2. **購入記録が端末の localStorage にしかない。** 別のスマホから見られない。機種変で消える。
   複数人で分担して記録しても合算できない
3. **住之江（jcd=12）決め打ち**
4. 予測と結果の照合が1日1回だけ

このうち **1 と 2 が今回の対象**。3 はその次（場ごとに1コース1着率が違うため、
コース補正を場別に較正し直す必要がある）。

## 動かしてはいけない制約

- **アプリは静的エクスポート**（`output: 'export'` / `vercel.json` の `framework: null`）。
  サーバー機能を1つも使っていない。これが**オフラインで全機能が動く**ことの土台になっている
- **Service Worker は `out/` を走査して自動生成**している。ここは過去に本番で404を踏んだ箇所
  （`vercel.json` を消すと `/sw.js` が消える）。触るリスクが高い
- **現地の回線は不安定。** 記録の書き込みがネット必須になってはいけない

## 3つの案

### 案A: アプリを Next.js のサーバーあり構成に変える

API ルートと Vercel Cron を1つのプロジェクトに置ける。

- ✅ 構成が1つにまとまる
- ❌ `output: 'export'` をやめることになり、SW のプリキャッシュ一覧の作り方が変わる。
  オフライン要件と真正面からぶつかる。**過去に本番で壊した箇所**

**採らない。** 得るものに対して壊す範囲が大きすぎる。

### 案B: 静的アプリはそのまま、収集だけ別のサーバーレスに出す

Vercel に2つ目のプロジェクトを作り、Cron と API を置く。

- ✅ アプリ本体は無傷
- ❌ デプロイ先が2つに増える。記録の読み書きのために結局 DB が要る

### 案C（推奨）: 収集は GitHub Actions、記録は BaaS に直接

- **収集**: GitHub Actions のスケジュール実行で、いまのスクリプトをそのまま回す。
  終わったら Vercel にデプロイする。**PCの起動が要らなくなる**
- **記録**: Supabase など、REST で直接読み書きできるものを使う。
  静的アプリのままクライアントから叩けるので、**サーバー機能を足さずに済む**
- **オフライン**: いままで通り localStorage に書き、オンラインになったら同期する
  （localStorage が正、DB は控え）。現地で電波が無くても記録できることを崩さない

- ✅ 静的エクスポートも SW もそのまま
- ✅ PC依存が消える
- ✅ 別端末から見られる
- ❌ アカウントが2つ要る（GitHub Actions のシークレット、Supabase）
- ❌ クライアントに公開キーが載るので、行レベルのアクセス制御が必須

**案C を推奨する。** 壊す範囲がいちばん小さく、壁1と壁2を同時に解ける。

## 決めてもらう必要があること

**アカウント作成と認証情報の登録は、私にはできない（安全上そうしている）。**
以下はユーザー側の作業になる。

1. **Supabase（または同等）のアカウント**を作るか。作るなら私が必要なテーブル定義と
   アクセス制御の SQL を用意する
2. **Vercel のデプロイトークン**を GitHub のシークレットに登録すること
   （GitHub Actions からデプロイするため）
3. **記録を誰が見られるか。** URLを知っていれば誰でも読み書きできる形でよいか、
   端末ごとの鍵を持たせるか。同行者と共有したいなら前者、自分だけなら後者

3 が決まらないとテーブル設計が決まらないので、**ここが最初の分岐**。

## 段階

| 段階 | 中身 | Claude 工数 |
|---|---|---|
| 1 | GitHub Actions で収集を回す（記録はまだ localStorage のまま） | 約30〜40分 |
| 2 | DB のテーブルとアクセス制御を用意し、記録の同期を入れる | 約60〜90分 |
| 3 | 同期の競合処理（複数端末で同じレースを触ったとき）とオフライン再送 | 約40分 |

段階1だけでも**壁1が消える**（PCの起動が要らなくなる）ので、
アカウントの用意が済んでいなくても先に進められる。

- 蓄積しても控除率25%は超えない。目的は勝つことではなく、
